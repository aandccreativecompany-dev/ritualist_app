Ritualist: getting from these screens to the Play Store

A manual, step-by-step path. Steps 1–3 are one-time setup, 4–8 are the build, 9–12 are publishing, 13 is the update loop. The appendix covers releasing from GitHub instead, with no Play Console fee.

Prepared 23 August 2026 · design source: AC Planner App.dc.html · repo: aandccreativecompany-dev/aandccreativecompany

Read first

The Play Store accepts a compiled Android app, not HTML screens. Somebody has to write the app code — either you, learning Flutter, or a developer you hire. Everything below assumes Flutter, because one codebase covers Android now and iOS later, and its widget model maps cleanly onto the card-stack design. Budget four to eight weeks of build time for the full screen set, or two weeks for a first version with planner, habits, mantras and reminders only.

Part one · Accounts and repository

Step 1 — Open a Google Play developer account

Go to play.google.com/console, sign in with the Google account you want to own the app forever (use a company account, not a personal one you might lose), and pay the one-time 25 USD registration fee. You will be asked to verify identity and address; verification can take a few days, so do this first while the app is still being built.

Choose the account type carefully. An organisation account needs a D-U-N-S number for A&C Creative Company but is exempt from the closed-testing gate. A personal account is faster to open, but personal developer accounts created after November 13, 2023 must run a closed test with at least 12 testers opted in continuously for the last 14 days before they can apply for production access. If you can produce a D-U-N-S number, the organisation route saves you two weeks and a tester hunt.

While you are in there, also set up a payments profile — you cannot sell a subscription without one.

Step 2 — Create the app repository on GitHub

Keep the app code separate from the website repo. Create a new private repository, for example aandccreativecompany-dev/ritualist-app, with a main branch. Two branches is enough: main is what ships, dev is where work happens.

Commit the design reference into the repo as design/ so the developer always has the screens beside the code.

Step 3 — Install the toolchain

On the machine that will build the app: install Flutter (which pulls the Dart SDK), Android Studio with the Android SDK and command-line tools, and Git. Then run flutter doctor and clear every warning it prints before writing a line of app code.

Create the project with flutter create --org ai.aandccreative ritualist. The package name it generates, ai.aandccreative.ritualist, is permanent once published — you cannot rename it later, so decide now.

Part two · Building the app

Step 4 — Set the design foundation

Before building screens, translate the design into a Flutter theme so every screen inherits it: ink #1B0F33, violet #4C2A85, gold #F2B93B for dark and #E0A419 for light, cream #FAF4E9, Archivo Black for headings, Inter for everything else. Define both a light and a dark ThemeData and set themeMode: ThemeMode.system, with a stored override for the settings toggle.

Data lives on the device first: a local database for plans, habits, mantras and journal entries, so the app works offline. Add cloud sync only when you want the same account on two devices.

Step 6 — Wire the reminders properly

This is the feature most likely to break silently, so treat it as its own piece of work. Use local scheduled notifications, not server push — the mantra and task list are already on the device, and local notifications keep working with no network and no backend cost.

The three schedules from screen 2s: 7:30 am mantra with the top three priorities, 1 pm check that fires only if something is still open, 9 pm close-the-day. Ask for notification permission the first time the user turns reminders on, never at launch. Request exact-alarm handling and battery-optimisation exemption where the phone demands it, and reschedule everything on device reboot.

Test on a real Xiaomi, Samsung and Oppo device. Aggressive battery managers on those brands are the usual reason a reminder never arrives.

Step 7 — Set up the subscription

In Play Console, under Monetise → Subscriptions, create one subscription with a monthly and an annual base plan, and attach a 14-day free trial offer to each. Then integrate Google Play Billing in the app so the paywall on screen 2m reads its prices live from Play rather than hard-coding them.

Part three · Publishing

Step 8 — Create the signing key

Generate an upload keystore once with keytool and point the Gradle release config at it. Opt in to Play App Signing when you create the app in Console.

Never commit the keystore or its passwords to GitHub. Add them to .gitignore, keep an offline backup, and store the passwords in a password manager. Lose the upload key and you must ask Google to reset it; lose access to the account and the app is unrecoverable.

Step 9 — Build the release bundle

Run flutter build appbundle --release. Play requires an Android App Bundle (.aab), not an APK. Set targetSdk 36 — starting August 31, 2026, new apps and app updates must target Android 16 (API level 36) or higher to be submitted to Google Play — and minSdk 24 to cover older phones.

Every upload needs a higher versionCode than the last. Bump it on every release without exception; Play rejects duplicates.

Step 10 — Fill in the store listing

Create the app in Console, then work through the Dashboard checklist. Screen 2t holds the assets: app name, short description, feature graphic at 1024×500, and the phone screenshots. You will additionally need a 512×512 app icon, a long description, a privacy policy hosted on aandccreative.ai, the content rating questionnaire, the data safety form declaring what the app stores, and the ads declaration (none).

The data safety form is where most first submissions get delayed. Answer it against what the app actually collects — journal text, habit history, email address — and keep the privacy policy consistent with it.

Step 11 — Test internally, then in closed testing

Upload the .aab to the Internal testing track first and add your own devices. Install through the opt-in link, and check the reminders across a full day, a light-and-dark theme switch, biometric unlock, and a trial purchase against a test account.

Then promote to Closed testing. If you registered a personal account, this track is the gate: recruit 15 to 18 people so you keep 12 after drop-outs, send them the opt-in link, and ask them to actually use the app daily. The 14-day countdown starts only after your release is approved by Google and at least 12 testers have opted in, and tester engagement is assessed separately when Google reviews the application — so silent testers can cost you the application even when the count is met.

After 14 continuous days, apply for production access from the Console dashboard.

Step 12 — Release to production

Create a production release, attach the bundle, write the release notes, pick the countries, and submit. Review usually takes a few days for a first submission. Roll out to a staged percentage — 20 per cent for a couple of days, watching the crash and ANR numbers — before going to 100 per cent.

Part four · Updates

Step 13 — The loop, done manually

Change the design here, commit the code change on the dev branch, merge into main, bump the version, rebuild the bundle, upload it to internal testing, check it, then promote the same build to production. Once you have shipped once, an update takes under an hour.

Automate it later, not now. When the manual loop is boring, add a GitHub Actions workflow that builds the bundle on every push to main and uploads it to the internal track through a Play service account. Keep the promotion to production a human click — an automatic path from a merge to every user's phone is a bug waiting for an audience.

Appendix · Releasing from GitHub instead

This is the no-fee route: the same app, built as an APK, attached to a GitHub Release, installed by hand. Use it to get the app into real hands now and move to Play later when you want to charge money or reach strangers. Steps 1 to 6 above still apply — only the publishing half changes.

What you give up: no subscription billing (Google Play Billing only works for apps installed from Play), no automatic updates, a Play Protect warning at install, and no discovery through search or ratings. Keep the paywall screen built but leave it switched off in this build.

A1 — Build a signed APK, not a bundle

Run flutter build apk --release. The output lands at build/app/outputs/flutter-apk/app-release.apk. Sign it with the same keystore from step 8 and keep that keystore safe — if you later switch to Play, or ship a second version here, a different key means users must uninstall and lose their data before they can install. Rename the file to ritualist-1.0.0.apk so the version is visible in the download.

A2 — Publish the release

The repository must be public for people to download without a GitHub account. If you would rather keep the code private, make a second public repo called ritualist-releases that holds only the APKs and a README.

Tag the commit v1.0.0, open Releases → Draft a new release, attach the APK, and write release notes in plain language for users, not commit messages. The permanent link to the newest build is github.com/<org>/<repo>/releases/latest — that is the URL to put on the website and in your WhatsApp message.

A3 — Write the install instructions

Most people have never sideloaded an app, so spell it out in the release notes: download the APK; when the phone asks, allow installs from this source for the browser; if a screen says the app is unsafe or unrecognised, choose Install anyway or More details → Install anyway; open Ritualist and allow notifications so the reminders arrive.

Expect to lose people at the Play Protect warning. Saying up front that the warning is normal for apps outside the Play Store recovers a good share of them.

A4 — Solve updates

Build an update check into the app: on launch, call api.github.com/repos/<org>/<repo>/releases/latest, compare the tag against the installed version, and if it is newer show a small card on the home stack offering the download. It is roughly fifty lines of code and it is the difference between users staying current and users stranded on version one.

Mention Obtainium in the release notes as the option for anyone comfortable with it: they point it at the repo once and it updates the app automatically from then on.

A5 — Automate the release build

This is where GitHub Actions earns its keep straight away. Add a workflow that triggers on a pushed tag matching v*, builds the release APK, and attaches it to the release automatically. Store the keystore as a base64 repository secret along with its passwords, so the signing key never sits in the repo. After that, pushing a tag is the entire publish step.
